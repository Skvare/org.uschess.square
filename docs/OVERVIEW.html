CiviCRM extension · org.uschess.square

Square Payment Processor

Lets US Chess Federation's CiviCRM take one-time and recurring dues, entry fees, and donations through Square — card data tokenizes in the browser and never touches the CiviCRM server.

v1.2.0 · beta CiviCRM 6.16+ PHP 8.2+ Square API 2025-01-15 AGPL-3.0-or-later

Overview

What this extension does

org.uschess.square registers Square as a CiviCRM payment processor type — the same role Stripe or PayPal extensions play — so contribution pages, event registration, and back-office forms can charge a Square-issued card without CiviCRM ever seeing the card number.

It depends on two core CiviCRM extensions, mjwshared and civi_contribute, and is built against CiviCRM 6.16 or later. Composer dependencies ship committed in vendor/, so installing it is a normal extension enable — no build step. It is maintained by US Chess Federation and developed by Skvare, distributed under AGPL-3.0-or-later.

Why it exists: US Chess needed dues, tournament entry, and donation payments to run through Square rather than the processors CiviCRM ships with out of the box, with the same card-on-file and recurring-billing experience members already expect from CiviCRM's native processors.

How it works

Two loops: charge now, reconcile later

A payment has a synchronous half — tokenize the card and ask Square to charge it — and an asynchronous half, where Square reports what actually happened via webhook. The extension is built around keeping those two halves correctly linked.

Recurring contributions add one more step before the top row: the processor creates (or reuses) a Square Catalog plan and plan variation for the billing cadence, then creates a Square Subscription linked to the card-on-file. The first charge happens immediately; every renewal after that is Square's clock, reported back through the same webhook loop.

Capabilities

What it handles

One-time payments

Card charges through Square's Payments API for contributions, event fees, and donations.

Recurring contributions

Square Subscriptions API drives renewals; eight cadences from daily to annual.

Refunds

Full and partial refunds issued through Square's Refunds API from the CiviCRM contribution.

Subscription changes

Cancellations and amount updates made in CiviCRM sync forward to the live Square subscription.

Card-on-file

Cards save as standard CiviCRM PaymentToken records — one contact can hold several across processors.

Customer deduplication

Square customers are matched and reused by email and reference ID instead of duplicating on every charge.

Webhook reconciliation

Every Square event is signature-verified, deduplicated, queued, and logged before it touches a record.

Sandbox & production

Fully separate credentials and data per environment, switchable per processor instance.

Data & storage

Who owns what data

The extension is deliberately thin on its own storage. It keeps exactly one table for itself — mapping a contact to a Square customer, per processor — and puts everything else into tables CiviCRM core already owns and understands.

DataTableOwner
Square customer mappingsquare_customer_mapThis extension — created on install, dropped on uninstall
Card-on-file referencecivicrm_payment_tokenCiviCRM core — never dropped
Recurring contributioncivicrm_contribution_recurCiviCRM core
Webhook queue & statecivicrm_paymentprocessor_webhookCiviCRM core — never dropped

Customer mappings key on (contact_id, payment_processor_id), so sandbox, production, and multiple Square merchant accounts stay separate rather than colliding on one contact field. An earlier version stored the customer ID as a Contact custom field; the upgrader migrates that data automatically only when it can be attributed to exactly one configured Square processor, and logs the rest for manual review rather than guessing.

Webhook events

What Square tells CiviCRM, and when

Square posts to https://your-site.org/civicrm/payment/ipn/{processor_id}. The X-Square-Hmacsha256-Signature header is validated before anything is queued; a failed record stays in the queue for the Process Pending Webhooks scheduled job to retry.

EventAction
subscription.createdSyncs subscription status to ContributionRecur
subscription.updatedSyncs subscription status/amount to ContributionRecur
subscription.canceledMarks ContributionRecur as Cancelled
invoice.createdCreates a Pending contribution for the upcoming invoice
invoice.payment_madeReconciles the paid invoice
invoice.payment_failedReconciles the failed invoice
payment.updatedReconciles an existing contribution
refund.createdReconciles a refund

Configuration

Setting up a processor

Created at Administer → System Settings → Payment Processors, type Square. Sandbox and live fields are entered separately and never share values.

FieldSource
Application IDDeveloper Dashboard → Your Application → Credentials
Access TokenLive or sandbox token, same dashboard

How it was built

Development workflow

The extension is scaffolded on civix (square.civix.php) against CiviCRM's mixin system — mgd-php for the managed payment-processor-type entity, setting-php for the debug-logging setting, scan-classes for autoloading. It targets PHP 8.2+ and follows CiviCRM's own two-space, Drupal-derived style rather than a generic PSR preset, so it reads consistently with the rest of a CiviCRM codebase.

Two checks gate a change, run from the extension root:

$vendor/bin/phpcs --standard=phpcs.xml.dist CRM square.php settings managed tests
$vendor/bin/phpunit --configuration tests/phpunit/phpunit.xml.dist

phpcs.xml.dist is the authoritative lint config — it deliberately permits CiviCRM conventions a generic linter would flag: CRM_* class names, snake_case hook functions, the ExtensionUtil as E pattern, and underscore-prefixed properties inherited from core's payment base class. vendor/ is committed rather than built, and is never linted or auto-formatted.

Handling secrets in development: access tokens, webhook signature keys, card nonces, and unredacted Square API responses are kept out of source, fixtures, logs, and tickets — including while debug logging is temporarily enabled to investigate a live issue.

Going live

Sandbox first, always

Square's HMAC signature covers the exact notification URL and raw request body, so the URL configured in Square and the one CiviCRM actually serves have to match byte-for-byte — no proxy rewrite, scheme change, or trailing-slash difference.

  1. Enable mjwshared and civi_contribute, then enable this extension.
  2. Create a Square payment processor in CiviCRM with sandbox Application ID, Access Token, Location ID, and Webhook Signature Key.
  3. In the Square Developer Dashboard, create a webhook subscription for that same sandbox application pointed at /civicrm/payment/ipn/{processor_id}.
  4. Subscribe to the eight events listed above — anything else is acknowledged but intentionally ignored.
  5. Confirm CiviCRM's Process Pending Webhooks scheduled job is enabled, to retry failed deliveries.
  6. Run a test one-time contribution, and a test recurring one if it's in scope. Check the contribution, payment token, recurring record, and webhook queue all landed correctly.
  7. Only after sandbox checks out, repeat the setup with the production Square application and live credentials.

Operations

When something doesn't reconcile

Webhook delivery and processing state live in civicrm_paymentprocessor_webhook. Start with records where status = error, alongside the CiviCRM log.

SymptomCheck
Webhook returns 401Signature key and notification URL match exactly; the raw body wasn't trimmed or transformed en route.
Webhook returns 400Square is posting valid JSON.
No change after a webhookEvent type is supported, processor ID in the URL is correct, queue record isn't stuck in error.
Repeated webhook deliveryA failed queue record with an unresolved error — Square keeps retrying until it succeeds.
Card field doesn't appearProcessor is Square, on-site collection is enabled, no CSP errors blocking the SDK script.
Sandbox data missing in live modeExpected — sandbox and production are entirely separate customers, cards, and credentials.
